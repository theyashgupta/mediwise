# Languages in the web app

The web app shows its interface in English or Hindi. English is the default. MEDI-64 is step 1: the app shell, the pages, the forms, the buttons and the empty and error states are in Hindi. MEDI-66 is step 2: catalog text, engine sentences and the Claude-written report text are in Hindi too. The section "What stays in English" lists the rest and gives the reasons.

## How it works

- `apps/web/src/config/messages/en/<namespace>.ts` holds the English text. `hi/<namespace>.ts` holds the Hindi text. There is one namespace per module, plus `common` (shared components) and `shell` (layouts).
- The Hindi file has the type `Messages["<namespace>"]`, so TypeScript rejects a missing key, an extra key or a function with different parameters.
- A component calls `useT()` from `@/common/hooks/use-locale` and reads `t.<namespace>.<key>`. A component that calls `useT()` renders again when the language changes.
- Code outside React (a toast, a zod message, a label helper) calls `getT()` when it shows the text. Do not call `getT()` at module load, because the text then stays in the language of the first load.
- A message with values is a function: `deleted: (name: string) => \`We deleted ${name}.\``.
- Plurals use `plural(locale, count, { one, other })`. It uses `Intl.PluralRules`, so Hindi gets the "one" form for 0 and 1.
- Dates and numbers use `getIntlTag()`: `en-IN` for English, `hi-IN-u-nu-latn` for Hindi. The `nu-latn` part keeps Latin digits, because lab reports print Latin digits.
- The language is stored in `localStorage` (key `locale`) and in the Supabase `user_metadata.locale` of the account. At sign-in, the account value wins. An account without a value takes the value of the device, for example a choice made on the sign-in page.
- `index.html` sets `<html lang>` from storage before the first paint. `setLocale` changes it on a switch, so screen readers use the correct voice.
- The switch is in Settings, Language, and on the sign-in page.

## Add a string

1. Add the English text to `en/<namespace>.ts`. Follow `.claude/rules/copy.md`.
2. Add the Hindi text with the same key to `hi/<namespace>.ts`. Follow the Hindi rules below.
3. Use it in the component: `const t = useT();` then `{t.<namespace>.<key>}`.
4. Run `pnpm check`. Two tests in `config/messages/messages.test.ts` fail when a step is missing:
   - "the English and Hindi message files have the same keys".
   - "no user-facing text in apps/web/src sits outside the message files". It reads every `.ts` and `.tsx` file and finds JSX text, copy attributes (`aria-label`, `title`, `placeholder`, `alt` and others), copy properties (`label`, `title`, `description`, `message`, `body`, `placeholder`) and toast calls with literal text.

## Add a language

1. Add the code to `locales` and a name in its own script to `localeNames` in `config/messages/locales.ts`. Add its Intl tag to `intlTag`.
2. Copy `hi/` to a new folder, translate every file, and add the locale to `messages` in `config/messages/index.ts`.
3. Add the code to the `lang` line in `apps/web/index.html`.
4. Extend the "contains Devanagari" test to the script of the new language.

## Hindi rules

- Write in Devanagari. Keep numbers in Latin digits.
- Keep the names the lab prints, in Latin script: HbA1c, LDL, TSH, and also PDF, JPG, MB, MediWise, Google.
- Use everyday Hindi. Use the common loanword (रिपोर्ट, अपलोड, प्रोफ़ाइल) and not a Sanskrit coinage.
- The copy rules apply: 20 words or fewer per sentence, active voice, one instruction per sentence, no semicolons. Keep every hedge.
- Every Hindi string with letters contains Devanagari. A test checks this. A string that is only a printed name goes in `printedNames` in the test.
- Wrap a string in `review(...)` when a Hindi reviewer must check it: medical meaning, a hedge, consent, privacy, deletion, legal or money text, or any doubt. `grep -c "review(" apps/web/src/config/messages/hi/*.ts` counts the open items. When a reviewer approves a string, remove its `review(...)` call.

## Report text in Hindi

The web sends the language in the `Accept-Language` header of every API call (`lib/api.ts`). A switch of language refetches every query. The API writes these texts in that language:

| Text | Where the Hindi comes from |
|---|---|
| Marker copy (description, what it is, why it matters, what moves it, South Asian note) | `packages/engine/src/catalog/hi/<group>.ts`, one file per marker group. |
| Pattern name, description, what it suggests, what to do | `packages/engine/src/catalog/hi/patterns.ts`. |
| Verdict, follow-ups, alert headline, category labels | Templates in `packages/engine/src/localize.ts`. The verdict and the follow-ups are rebuilt from the stored English, so both languages show the same numbers. |
| Narrative, finding titles and bodies, doctor questions | Claude, once per report, in `apps/api/src/modules/narrative/narrative.hindi.ts`. |

### Claude-written text

- Claude translates the stored English text. It does not write new text from the engine facts, so the grounding checks of the English narrative and findings stay the only grounding checks.
- The web asks for the Hindi text the first time a Hindi user opens a done report (`POST /reports/:id/translation`). The report shows the English text and a note until the Hindi text is ready. The doctor export waits for it before it prints.
- The validator rejects an item when a sentence has more than 20 Devanagari words, when it has a semicolon or Devanagari digits, when a printed marker name or an acronym is missing, when a number changes, when a hedge is dropped, or when a diagnosis word is added. Rejected items go back to Claude alone, for up to two fix calls. After that the whole report stays in English, with a note.
- The result is stored in `reports.translations` (done or failed). A stored result is never paid for again. A new read of the report clears it.
- The tokens join the report's read job as the `translate` step, so the report cost and the monthly cap count them.
- Cost on the two anonymised samples (claude-haiku-5-5, 2026-10-13, 3 runs on each sample with the final prompt): 0.14 to 0.26 cents per report, mean 0.18 cents. The target is under 0.3 cents. 5 of 6 runs passed. The failed run still wrote printed marker names in Devanagari after three calls.

### Medical review

`docs/review/hindi-catalog.md` lists every Hindi catalog and engine sentence beside its English source, with one checkbox per marker. Run `pnpm --filter @mediwise/api review:hindi` after a change to a Hindi file. A test fails when the committed list is out of date.

## What stays in English

| Text | Why |
|---|---|
| Year in review intro, episode summaries | Claude writes them. Only the report text has a Hindi validator. |
| Printed study text (impression, findings) and printed lines in settled findings | The lab prints them in English. |
| Marker names, lab names, units | The lab prints them in English. |
| Report titles that MediWise makes (for example "1 Feb 2025 · blood panel (46 markers)") | The title is stored with the report and the user can change it. One stored text keeps the lists, the pickers, the export and the CSV the same. |
| API error messages (problem `title` and `detail`) | The API has no locale yet. |
| Policy pages (terms, privacy, refunds, contact) | Legal text needs a legal review before translation. The links and the page frame are in Hindi. |
| Auth emails (`supabase/templates`), the landing site (`apps/landing`), `index.html` meta tags | Out of scope for step 1. |
| Developer pages (`/design`, `/dev/kitchen-sink`, `modules/health`) | Only developers see them. The scanner skips them. |
| The operator page (`/admin`, `modules/admin`) | Only the admin account sees it. The scanner skips it. Its breadcrumb name is in both languages. |
| File names of downloads | A file name is not part of the interface. |
